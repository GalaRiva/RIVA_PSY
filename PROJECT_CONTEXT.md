    В самом ТЗ было два конфликтующих описания оплаты. Решение пользователя: **старая модель считается deprecated и не переносится на PWA.**

    - **~~Старая модель (DEPRECATED, не переносим)~~**: тарифы "Бесплатный"/"Полный доступ", месяц 9€/год 65€, промокоды, автопродление, оплата через Yookassa + In-App Purchase. Уже реализована в текущем Flutter-коде (`yookassa_payments_flutter`, `in_app_purchase`, `settings_buy_subscription_screen`, `settings_payment_subscription_screen`, `settings_tariff_activated_screen`, `tariff_model.dart`), но при переезде на PWA этот код и его бизнес-логику **не переносим и не используем как образец** — сама модель (App Store/Google Play IAP) физически неприменима к PWA.
    - **✅ Актуальная модель (единственная, для PWA)**:
      1. Оплата происходит **на сайте через Stripe Connect**, не в самом приложении/PWA.
      2. **До оплаты** — полностью free-тариф без регистрации: локальный анонимный `device_uuid` генерируется на клиенте без обращения к серверу; весь прогресс/избранное/история хранятся **только на устройстве** (в PWA — IndexedDB/localStorage, аналог Hive); сервер не получает никаких данных о бесплатном пользователе.
      3. **Регистрация происходит только в момент оплаты**: пользователь вводит email на сайте → passwordless / magic link (без пароля) → создаётся `user_id`, привязанный к Stripe Customer ID.
      4. Оплата подтверждается через Stripe webhooks (`checkout.session.completed`, `invoice.paid`, `customer.subscription.updated/deleted`) → backend обновляет статус подписки для `user_id`.
      5. После оплаты сайт показывает кнопку "Открыть в приложении" → **deep link / universal link** с одноразовым токеном → автологин в PWA, выдаётся JWT.
      6. **Миграция локальных данных на сервер**: однократно, локальные данные (привязанные к `device_uuid`) отправляются на сервер и привязываются к `user_id`; конфликты (повреждённые/задвоенные данные) разрешаются в пользу более полной/новой версии, лог конфликта сохраняется для отладки. После миграции `device_uuid` перестаёт быть основным идентификатором.
      7. Дальше приложение при каждом запросе проверяет статус подписки через собственный backend API (JWT-авторизация, не через Apple/Google). Синхронизация между устройствами — только для оплативших/зарегистрированных.
      8. Данные на сервере — минимальный набор: email, статус подписки, прогресс/контент-данные, привязанные к `user_id`, без лишних персональных полей.
    - **Технические зависимости новой модели** (ничего из этого в коде пока нет — строить с нуля под PWA): backend-эндпоинт приёма Stripe webhook; API проверки статуса подписки (JWT); эндпоинт миграции локальных данных (принимает `device_uuid` + payload, возвращает `user_id`); deep link/universal link конфигурация для автологина (на вебе это существенно проще — обычный URL + service worker, без нативных Universal Links/App Links).

### Оценка качества текущей реализации (разобрано 2026-07-22)

Функционально модуль закрывает весь цикл (добавить препарат → назначить время/период приёма → напоминание-попап → список актуальных/по дате → редактирование), и визуально консистентен с остальным приложением (переиспользует `CustomButton`, `CustomTextFormField`, `AppStyle`, `CustomAppBar`). Но по архитектуре и аккуратности кода это заметно наименее доработанная часть кодовой базы:

- **Хранение данных рискованное**: `PillsRepo.updateEvent()` при каждом сохранении **удаляет всю Hive-таблицу и переписывает её заново** поэлементно (`deleteBox` → цикл `setBox`), вместо точечного добавления/обновления одной записи. Если процесс прервётся между удалением и повторной записью — можно потерять все препараты целиком, не только изменяемый.
- **Чтение с побочным эффектом записи**: `PillsController.getPills()` — по сути геттер, но в конце вызывает `repo.updateEvent(pills)`, то есть каждое открытие экрана перезаписывает всё хранилище целиком. Нарушение разделения "чтение/запись", лишняя нагрузка и лишний риск потери данных на пустом месте.
- **Нет обработки ошибок**: чтение из Hive (`jsonDecode` на каждую запись) ничем не защищено — одна повреждённая запись уронет весь экран списка препаратов. Единственный `try/catch` в модуле (`setDurationOfReception`) просто делает `print()` и молча проглатывает ошибку, без обратной связи пользователю.
- **Дублирующая и рассинхронизированная логика**: метод `checkDateInRange` объявлен в двух местах (`PillsController` и `PillsBottomSheetController`) с **разной семантикой** — в одном месте окно ±1 день от даты начала курса, в другом — честная проверка "между start и end". Одинаковое имя, разное поведение — источник будущих багов.
- **Валидация времени приёма кустарная**: часы/минуты разбираются вручную по индексам строки (`text[0]+text[1]`), верхняя граница проверяется как "часы < 24" и "минуты < 60" вместо корректных 23/59 — на границе возможны некорректные значения времени.
- **"Мёртвый" код валидации формы**: в `PillsAddBottomSheet` объявлен `formKey = GlobalKey<FormState>()`, но никогда не оборачивается в `Form` и не вызывается `validate()` — то есть `validator` у текстового поля с названием препарата **фактически никогда не срабатывает**, хотя выглядит так, будто валидация есть.
- **Смешаны два UX-паттерна валидации в одном экране**: для названия препарата — обычный inline-error у текстового поля (`CustomTextFormField.validator`, но нерабочий, см. выше), а для времени приёма — модальное окно с сообщением об ошибке через смену цвета рамки на красный. Две разные идиомы там, где могла бы быть одна.
- **Не убранные следы кодогенерации**: пустые `// TODO: implement onInit`, `// TODO: implement updateTasks` (комментарии остались от исходного DhiWise-шаблона, реализация под ними уже есть, но комментарий не удалён), задвоенный `import` в `pills_list_model.dart` — по мелочи, но показывает, что модуль не получил той же полировки, что и более новые части (например "Обретение").
- **Архитектурно самый "старый" слой**: чистый GetX с ручными вызовами `update()` по всему коду — паттерн более раннего поколения приложения. Более новые фичи ("Обретение": `working_out_irrational`, `happiness_in_focus`, `desires`) уже написаны на `flutter_bloc`/Cubit. Pills остался на старом подходе и не мигрировал вместе с остальными.

**Что стоит сделать иначе при переносе на PWA** (не просто 1:1 переписать, а поправить по ходу):
1. Инкрементальное хранение (добавить/обновить/удалить одну запись в IndexedDB), без полной перезаписи всей коллекции на каждое действие.
2. Убрать побочный эффект записи из операции чтения списка препаратов.
3. Добавить реальную обработку ошибок чтения (устойчивость к повреждённой записи) с понятной обратной связью пользователю вместо silent-fail.
4. Свести валидацию времени к одной корректной реализации (0-23 / 0-59) и к одной UX-идиоме (либо везде inline-ошибки в форме, либо везде модалка — не вперемешку).
5. Либо реально подключить `Form`/`formKey` и `validate()`, либо убрать эту неработающую обвязку, чтобы не создавать ложное ощущение проверки.
6. Убрать дублирующийся `checkDateInRange` с разной семантикой, оставить одну корректную версию.
7. Реализовать состояние на том же стеке, что и остальной PWA (не тащить GetX-паттерн как единственно ради "было так во Flutter") — иначе Pills снова останется архитектурным аутсайдером в новом кодовом стеке.
8. Механизм напоминаний в любом случае переписывается с нуля под веб (Push API + Service Worker вместо `workmanager`) — это уже входит в общий план миграции, но именно в Pills напоминание вызывается напрямую (`WorkManagerService().initService()` из `addPill`), так что стоит сразу закладывать архитектуру напоминаний с учётом и этого модуля, а не только основного дневника.

## 5. Что переносимо / что переписывать заново для PWA

**Переносимо как концепция / 1:1 переиспользуемо в виде спецификации** (не как код, а как источник истины по неймингу и структуре):
- Иерархия сущностей и их названия: эмоции (группы/подгруппы/конкретные эмоции), места, персоны, части тела, записи (СМЭР), тарифы — модели данных (`*_model.dart`, `freezed`-классы) читаемы как спецификация полей даже если Dart-код не используется напрямую.
- Разбиение на экраны и порядок навигации Основного пути — это чистый UX-флоу, воспроизводимый в любом фреймворке.
- Структура графиков (7 типов, что откуда берут данные) — бизнес-логика агрегации переносима как алгоритм (пересчитать на TS/SQL/что угодно).
- Дизайн-токены: `app_style.dart` / `app_decoration.dart` (566+370 строк) — цвета, текстовые стили, отступы, скорее всего экспортируемы в CSS-переменные / Tailwind-конфиг вручную (не автоматически, но как источник).
- Тексты, копирайтинг (все "тёплые" сообщения-подбадривания из ТЗ и Figma) — переносятся как есть.
- Названия роутов/экранов (`k1`...`k70`) — полезны как чек-лист "что вообще нужно построить", по одному экрану на пункт.

**Нужно писать заново (Flutter-специфика, не переносится на веб напрямую)**:
- Вся Flutter Widget-разметка (`*_screen.dart`, `*_widget.dart`) — просто UI-код, придётся верстать заново под веб-стек (React/Vue/etc.).
- GetX/flutter_bloc/provider — состояние управления, замена на веб-стейт-менеджер (Redux/Zustand/Context/etc.).
- Hive/SharedPreferences — заменяются на IndexedDB/localStorage/веб-совместимое хранилище.
- Firebase Auth платформенные SDK (Google/Apple sign-in нативные потоки) — на вебе другой OAuth-флоу (Firebase Web SDK или отдельный auth-провайдер).
- just_audio/flutter_sound/record (запись голоса) — на вебе через MediaRecorder API/Web Audio API, другая реализация.
- awesome_notifications/flutter_local_notifications — на вебе Push API + Service Worker (принципиально другая модель, тем более для PWA это ключевая история).
- workmanager (фоновые задачи) — на вебе через Service Worker/Background Sync, сильно ограниченные возможности по сравнению с мобильной ОС.
- yookassa_payments_flutter/in_app_purchase — не нужны вовсе при новой (веб) модели оплаты из ТЗ; строить Stripe-интеграцию с нуля под веб — что фактически совпадает с тем, что и так предписывает актуальная версия ТЗ.
- pdf/printing (генерация PDF) — на вебе другой инструмент (напр. jsPDF/Puppeteer/серверная генерация).
- circular_slider/sleek_circular_slider (кастомный тач-регулятор) — придётся реализовать заново на канвасе/SVG под веб-ввод (мышь+тач).
- syncfusion_flutter_charts/pie_chart — заменить на веб-чартинг библиотеку (Recharts/D3/Chart.js/etc.), логика графиков (что и как считать) переносится, рендеринг — нет.
- Deep link/Universal Links механизм — на PWA заменяется обычными URL + service worker, сильно проще технически.
- Вся нативная обвязка (Podfile, GoogleService-Info.plist, android/ каталог, xcodeproj) — не нужна для PWA вообще.

### 35. `flutter run` в фоне через именованный пайп (FIFO) — находка про однократный `cat`-reader (2026-07-25)

Во время сессии поэкранной локализации UI (коммит `5fd946c` на `pre-pwa-migration-snapshot`, 2026-07-25) использовался `flutter run -d <device> --debug` в фоне с интерактивной подачей команд `r`/`R` (hot reload/restart) через именованный пайп из отдельных вызовов инструмента, например:

```bash
mkfifo /tmp/flutter_run_input
(cat /tmp/flutter_run_input; sleep 999999) | flutter run -d emulator-5554 --debug > /tmp/flutter_run_session.log 2>&1 &
# в другом вызове, позже:
printf 'R' > /tmp/flutter_run_input
```

**Проблема:** такая схема работает только один раз. `cat` читает из FIFO до EOF, который наступает сразу после того, как писатель (`printf ... > fifo`) закрывает файл — то есть после самой первой команды `cat` завершается и выходит. Обёртка `(cat fifo; sleep 999999)` не спасает: `sleep 999999` ничего не делает с пайпом, он просто держит процесс живым, но уже не читает. В результате первая отправленная команда (`R`) доходит до `flutter run` и честно перезапускает приложение, а все последующие `printf 'R' > /tmp/flutter_run_input` **блокируются навечно** в ожидании открытия FIFO на чтение — реального читателя больше нет. Симптом со стороны: вызов инструмента с записью в пайп зависает и уходит по таймауту в фон, а в логе `flutter run` не появляется новая строка `Performing hot restart...`/`Restarted application in ...` — визуально выглядит так, будто изменения в коде не подхватились, хотя на самом деле команда перезапуска просто не была доставлена.

**Фикс — заменить `cat` на `tail -f`:**

```bash
mkfifo /tmp/flutter_run_input
tail -f /tmp/flutter_run_input | flutter run -d emulator-5554 --debug > /tmp/flutter_run_session.log 2>&1 &
```

`tail -f` не завершается на EOF — он продолжает ждать новые данные в файле вечно, поэтому одного и того же процесса-читателя хватает на весь сеанс `flutter run`, сколько бы раз ни отправлялись `printf 'r'`/`printf 'R'` в файл пайпа. Побочный нюанс, на который стоит обратить внимание при повторении: если случайно запустить `tail -f fifo` дважды (например, тестовым запуском в фоне "для проверки", не убив его перед основным запуском) — оба процесса будут читателями одного FIFO одновременно, и записанные байты непредсказуемо достанутся то одному, то другому, из-за чего часть команд `r`/`R` будет "теряться" без явной ошибки. Перед стартом сессии стоит проверять `ps aux | grep "tail -f <путь-к-fifo>"` и держать ровно один читатель.

### 51. Критический баг: Google-вход — "успешная авторизация в никуда", исправлено, 2026-07-27

Обнаружено на реальном устройстве (Xiaomi Redmi 15C): `FirebaseAuth.instance.signInWithCredential(credential)` успешно создаёт пользователя (подтверждено в Firebase Console — новые записи в Authentication), но экран после выбора Google-аккаунта просто замирал — ни ошибки, ни перехода дальше. USB-отладка на устройстве не заработала (стандартные шаги — обычный переключатель, MIUI-специфичный "Отладка по USB (Настройки безопасности)", смена режима USB-подключения, отзыв разрешений, полная перезагрузка телефона — испробованы, диалог авторизации adb так и не появился), поэтому диагноз ставился чтением кода, без живого лога.

**Корневая причина — несовпадение типов исключений.** В `lib/presentation/initial_setup/sign_in/data/repository.dart` методы `checkUserState()` и `createUser()` делают запросы к Firestore (`.get()`/`.set()` на коллекциях `Users`/`UsersData`), но оборачивали их в `try { ... } on FirebaseAuthException catch (e) { ... }`. `FirebaseAuthException` — тип из пакета `firebase_auth`; Firestore-операции бросают `FirebaseException` из `cloud_firestore` — при том что `FirebaseAuthException extends FirebaseException`, узкий `on FirebaseAuthException` не перехватывает обычный `FirebaseException`, только его подтип. Любая Firestore-ошибка (правила безопасности, сеть, права) пролетала мимо этого catch.

**Усугубляющий фактор.** `k2_controller.dart:authWithGoogle(context)` — вызывающая цепочка (`SignInWithGoogle` → `CheckUserState`/`CreateUser` → `GetAndSetRemoteDataLocally`) — не была обёрнута вообще ни в какой try/catch. Долетевшее снизу необработанное исключение превращалось в silent uncaught Future error: Flutter логирует его в consle/zone-handler (недоступно без USB-лога), но никакого `showMessage()` или `Navigator.push...` не происходит — экран просто остаётся как есть. Это и есть механизм "успешной авторизации в никуда".

**Исправлено:**
- `repository.dart`: в `checkUserState()` и `createUser()` добавлен второй catch — `on FirebaseException catch (e) { print(e); ... }`, возвращающий явный `FirebaseUserResult` с `FirebaseResultStatus.Error` (используя `AuthExceptionHandler.generateErrorMessage(AuthStatus.unknown)` — тот же дефолтный текст, что и для прочих неопознанных ошибок в этом файле) вместо того, чтобы исключение улетало дальше необработанным.
- `k2_controller.dart:authWithGoogle(context)`: вся цепочка обёрнута в try/catch; при любом непойманном исключении — `print(e)` + `showMessage(context, title: 'Регистрация', content: 'network_error_try_later'.tr())` (переиспользован существующий ключ, уже применявшийся сегодня в §46 для похожих сетевых ошибок). Добавлен импорт `easy_localization`.

**Проверено на предмет того же паттерна в остальном коде (по прямому запросу) — найдено ещё 2 места, НЕ исправлены, требуют отдельного подтверждения:**
- `repository.dart:resetUserPassword()` — Firestore `.update()` внутри `on FirebaseAuthException catch` — идентичная уязвимость, но в потоке сброса пароля, не входа.
- `k2_controller.dart:authWithApple(context)` — структурно идентична `authWithGoogle` (тот же `CheckUserState`/`CreateUser`, теперь безопасные благодаря фиксу выше), но сама функция тоже не обёрнута в try/catch — остаточный риск от любых других исключений в цепочке (например из `CurrentUser.repo.setService()`/`setLocalUserData()`).

**Проверено и признано безопасным, изменений не требует:**
- `signUpWithEmail`, `signInWithEmail`, `confirmResetCodeForEmail`, `sendResetPasswordCodeEmail`, `verifyResetCodeForEmail` в `repository.dart` — узкий `on FirebaseAuthException` там корректен, эти методы делают только чистые `FirebaseAuth`-вызовы, Firestore не трогают.

- `getAndSetRemoteUserLocally()` (usecase `GetAndSetRemoteDataLocally`, вызывается из обоих flow) — уже использует широкий `catch (_)`, не источник тишины (это тот самый метод, что показывал диалог "Ошибка сохранения данных, попробуйте ещё раз" при более раннем в этой же сессии инциденте с отключённым Firestore API).

- Логика `k1_controller.dart` (сплэш) — сама по себе корректна, но это не то место, где решается судьба сессии: `initialRoute` выбирается раньше, в `main.dart`, до того как сплэш вообще запускается.

**Найденная причина** — `main.dart:60` (до фикса):
```dart
await Firebase.initializeApp();
...
await HiveDB.initDB();
...
final event = await FirebaseAuth.instance.currentUser;
if (event == null)
  AppRoutes.initialRoute = AppRoutes.signUp;
else
  AppRoutes.initialRoute = AppRoutes.splashScreen;
```
`FirebaseAuth.instance.currentUser` — обычный **синхронный** геттер (`User?`, не `Future`). На Android восстановление сохранённой сессии из нативного хранилища после `Firebase.initializeApp()` происходит **асинхронно** внутри SDK и не гарантированно успевает завершиться к моменту, когда этот геттер читается. Единственная пауза между `initializeApp()` и чтением `currentUser` — это `await HiveDB.initDB()` (открытие локальной Hive-базы, обычно быстрая операция без сети). Иногда этой паузы хватало (сессия успевала восстановиться) — отсюда нестабильность симптома, иногда нет — и тогда полностью валидная, не истёкшая сессия читалась как `null`, и `initialRoute` уходил на `AppRoutes.signUp`, что для пользователя выглядит один в один как разлогин.

**Почему это не тот же баг, что A1**: A1 — гонка ВНУТРИ уже распознанной как залогиненной сессии (загрузка тарифа в `k1_controller.dart`, отдельный код). Этот баг — про то, распознаётся ли сессия вообще, и срабатывает раньше, в `main.dart`, до того как код из A1 хоть раз выполнится. Разные файлы, разные функции, разный момент жизненного цикла — фикс A1 никак не мог случайно вылечить это.

**Фикс** — заменить синхронное чтение на ожидание первого события потока состояния авторизации, которое гарантированно отражает уже устоявшееся состояние (а не промежуточное неготовое):
```dart
final event = await FirebaseAuth.instance.authStateChanges().first;
```

**Общий паттерн для будущего**: `FirebaseAuth.instance.currentUser` небезопасно читать синхронно сразу после `Firebase.initializeApp()` при принятии решений о навигации/маршрутизации на холодном старте — на Android нет гарантии, что нативное восстановление сессии уже завершилось к этому моменту, даже если между `initializeApp()` и чтением есть какой-то `await` (лёгкая локальная асинхронная операция вроде открытия Hive-базы может просто оказаться быстрее восстановления сессии). Правильный паттерн — либо `await FirebaseAuth.instance.authStateChanges().first`, либo подписка на поток с последующим rebuild UI, а не одноразовое синхронное чтение. Если где-то в проекте появится ещё один код, принимающий решение по `.currentUser` сразу на старте (а не после явного логина, где сессия гарантированно уже свежая) — проверить на этот же паттерн в первую очередь.

Она не пострадала. Гипотеза отклонена доказательно, не предположением.

**Настоящая причина — Android Auto Backup, подтверждено пользователем стопроцентно.** `AndroidManifest.xml` не содержал ни `android:allowBackup="false"`, ни файла правил `fullBackupContent`/`dataExtractionRules` — то есть был активен дефолтный авто-бэкап Android (резервное копирование приватных данных приложения в Google Drive пользователя). Hive хранит свои файлы под `getApplicationDocumentsDirectory()`, что попадает в область дефолтного бэкапа. Механизм: пользователь действительно делала полное удаление приложения перед тестом сборки `a87be9a` — но при установке того же пакета (`com.riva_psy.app`) с той же подписью на устройство, залогиненное в тот же Google-аккаунт, что использовался для входа в приложение, Android тихо восстановил приватные данные из облака, включая старый Hive-бокс событий, засеянный на русском в более ранних тестах. Это происходит на уровне ОС, полностью в обход прикладной логики "досеять бокс, если он пуст" — бокс приходил из бэкапа уже не пустым, код даже не пытался его пересеять. Пользователь проверила на телефоне (Google → Резервное копирование) — RIVA PSY действительно был в списке приложений с бэкапом; при отключении Google явно предупредил об удалении данных из аккаунта, подтвердив механизм. Старая резервная копия удалена вручную.

**Фикс**: `android:allowBackup="false"` в `AndroidManifest.xml`. Осознанный побочный эффект: пользователи, переходящие на новый телефон, больше не получат локальные данные автоматически через бэкап Google — это согласуется с уже принятым в проекте архитектурным решением про приватность данных (§ про "все данные хранятся на телефоне пользователя", см. модель тарифов и описания в `TariffModel`), поэтому оставлено как есть, не компенсировано отдельным ручным экспортом/импортом в рамках этой сессии.

**Категория находки**: не гонка (в отличие от A1/C1) — поведение ОС, тихо переживающее удаление приложения, которое прикладной код в принципе не может обнаружить или предотвратить изнутри логики "seed if empty".

### 57. НАСТОЯЩАЯ причина "нет рекомендаций в конце Пути" — поле `Audio.emotions` пустое у всех 64 документов, никогда не заполнялось

После нескольких раундов диагностики тарифа/userId()/локали (§55-56) — тариф и вход оказались ни при чём. Прямая проверка всех 64 документов коллекции `Audio` в Firestore: **у всех 64 поле `emotions` — пустая строка**. Никогда не заполнялось с момента заливки контента (§53), где скрипт `fb_write_firestore.py` жёстко писал `'emotions': ''` как плейсхолдер, который так и не заполнили реальными данными.

**Почему это ломает рекомендации везде, для всех, независимо от тарифа/аккаунта**: `Audio.fromJson()` (`lib/core/models/audio/audio.dart:19`) парсит поле так: `(json['emotions'] as String? ?? '').split(', ')` — для пустой строки `''.split(', ')` даёт `['']` (список с одной пустой строкой, не пустой список!). `ExerciseContentController.getAudios()` (`exercise_content/controller.dart`) сравнивает `audio.emotions` с каноническим русским именем текущей эмоции (`RuCanonicalName.forKey()`) — `['']` никогда не совпадёт ни с одним реальным именем эмоции. Результат: `mainAudios`/`additionalAudios` всегда пустые, для любого аккаунта, на любой сборке, независимо от тарифа, входа, локали — весь путь диагностики тарифа (A1, §55-56) был обходом реальной причины, тариф на самом деле был не виноват (это отдельно подтверждено: `tariffIsOrion()` реально возвращал `true` на диагностическом экране, а рекомендаций всё равно не было).

**Не почищено в этой сессии** — это развилка, а не однозначный баг-фикс, поэтому нужно решение пользователя, не додумывать самой:
- **Вариант A (контент)**: заполнить `emotions` у всех 64 аудио реальными названиями эмоций (на русском, через запятую, под тот же паттерн `.split(', ')`) — трудоёмко, но сохраняет задуманную точность подбора (конкретное аудио под конкретную под-эмоцию).
- **Вариант B (код)**: добавить фолбэк в `getAudios()` — если по `emotions` совпадений нет, показывать всё аудио с тем же `tab`, что и у выбранной эмоции (это поле у всех 64 документов заполнено корректно, проверено ещё в §53). Разблокирует рекомендации сразу, без ручной разметки, но менее точно (аудио на уровне категории эмоции, а не конкретной под-эмоции).

Дожидается решения пользователя, какой вариант (или оба — B как немедленный фолбэк, A как последующее уточнение) выбрать.

Следующий шаг (не начат) — разбор жизненного цикла `K1Screen`/`K1Controller`: `controller.initialization(context)` вызывается синхронно прямо в `build()` (побочный эффект внутри build — сам по себе не новость для этого проекта, см. паттерн в других контроллерах), `Get.put(K1Controller())` может переиспользовать уже существующий инстанс контроллера при повторных заходах на этот роут в рамках одной сессии (значения `wasInit`/`secondsToNewPage` тогда не сбрасываются к дефолтным), `secondsToNewPage` в отдельных ветках (`_downloadingFiles` завершился) принудительно обнуляется перед вызовом `timer(context)` — то есть навигация ДАЛЬШЕ может сработать без задержки в 2 секунды, отведённой на показ сплэша, но не сразу при первом заходе. Приостановлено пользователем — не блокирует план публикации, продолжить после.

**РЕШЕНО, 2026-08-02 — подтверждено чтением реального исходника пакета `get 4.6.6`, не догадкой.** `GetInstance()._insert()` (то, что вызывает `Get.put`) — если ключ (`K1Controller`, без тега) уже зарегистрирован и не помечен `isDirty`, **ничего не делает**, полностью игнорируя новый экземпляр:
```dart
if (_singl.containsKey(key)) {
  final dep = _singl[key];
  if (dep != null && dep.isDirty) { _singl[key] = _InstanceBuilderFactory<S>(...); }
  // иначе — no-op, старый инстанс остаётся
}
```
`isDirty` выставляется в `true` только через `RouterReportManager.reportRouteWillDispose()` — а этот хук подключается исключительно через `GetObserver` (`NavigatorObserver`), который регистрируется ТОЛЬКО через `GetMaterialApp`. Проверка `lib/main.dart` подтвердила: приложение использует обычный `MaterialApp`, не `GetMaterialApp` — то есть `GetObserver` нигде не подключён, и автоматическая очистка GetX-зависимостей **не работает вообще нигде в этом приложении**, не только на этом экране.

`grep -rn "AppRoutes.splashScreen"` по всему `lib/` показал: экран открывается не только один раз при холодном старте, а **при каждом логине и при каждой регистрации** (`sign_in_screen/k2_controller.dart`, `sign_up_screen/k2_controller.dart` — 10+ мест) и при переходе из уведомления о приёме таблеток (`message_box_with_central_icon.dart`). Это будничный, ежедневный путь, не редкий edge-case.

**Полная цепочка**: первый холодный старт создаёт `K1Controller` и он честно проходит `initialization()`, доходит до `timer(context)`, который в ветке завершённой загрузки файлов принудительно обнуляет `secondsToNewPage = 0` перед вызовом. Контроллер остаётся в памяти GetX навсегда (нечему его удалить). При следующем визите на `splashScreen` (например, после логина) `Get.put(K1Controller())` — no-op, переиспользуется тот же контроллер с `wasInit: true` и `secondsToNewPage: 0` — `initialization()` идёт по ветке `else timer(context)` и уходит с экрана СРАЗУ, без положенных 2 секунд — сплэш физически не успевает отрисовать ни одного кадра с картинкой. Это и есть «пустой экран 2» — не баг рендеринга, а навигационная гонка.

**Фикс** (`k1_screen.dart`) — принудительное пересоздание контроллера при каждом заходе, не полагаясь на автоочистку, которой в этом приложении нет:
```dart
Get.delete<K1Controller>();
final controller = Get.put(K1Controller());
```
`Get.delete` на первом заходе (когда ничего ещё не зарегистрировано) — безопасный no-op по коду самого пакета.

**Подтверждено пользователем на реальном устройстве, 2026-08-02** — включая промежуточный шаг: пользователь сообщила, что фикс `99036b7` НЕ помог при первой проверке, поэтому был добавлен грубый диагностический жёлтый баннер поверх экрана (build-timestamp + `wasInit`/`secondsToNewPage`/`loading`) в сборке `5b3f940`, а не продолжено гадание. ### 60. РЕШЕНО — настоящая причина полного отказа входа/регистрации через Google Play: три РАЗНЫХ сертификата подписи, ни один изначально не был зарегистрирован для Google Sign-In, 2026-08-05 — 2026-08-07

**Симптом**: реальные пользователи (и вход, и регистрация, через Google и Apple) получали общий диалог "Регистрация" с текстом "Произошла непредвиденная ошибка, проверьте подключение к интернету" — при этом та же самая сборка, установленная напрямую (sideload apk, не через Google Play), входила без проблем. Диагностика через `getIdToken(true)`/retry на чтение `Users` (см. коммит `271a747`) была правильным, но не единственным и не главным фиксом — гонка с claims в токене действительно существовала и была устранена, но не она вызывала симптом, о котором сообщал пользователь через Google Play.

**Почему диагностика (`e.toString()` в диалогах) несколько раз "не срабатывала", хотя код был на месте:**
1. Реальное исключение из `google_sign_in`/`sign_in_with_apple` SDK глоталось на уровень ниже, чем куда были добавлены первые диагностические `catch`-блоки — `ServicesAuthService.authWithGoogle()`/`authWithApple()` (`services/services_auth_service.dart`) ловили exception как `catch (_) { return false; }`, теряя его полностью, до того как он мог дойти до `repository.dart`/`k2_controller.dart`.
2. Даже после того как это поправили (сохранение текста в поле, временно всплывающее в `[DIAG:...]`) — несколько сборок подряд всё равно показывали старый generic-текст без всякого `[DIAG:...]`. Причина оказалась в гигиене самой сборки: `flutter build` без `flutter clean` между итерациями плюс R8/ProGuard-минификация (`minifyEnabled true` в `android/app/build.gradle`, без `keep`-правил для классов `google_sign_in`/`firebase-auth`, только `proguard-rules.pro` с правилами для WorkManager/Firebase ComponentRegistrar) — после полной пересборки с нуля (`flutter clean` + ручное удаление `build/`/`.dart_tool/`/`android/.gradle` + `flutter pub get`) и временного отключения минификации диагностика наконец сработала.

**Реальный текст ошибки, полученный на реальном устройстве через Google Play Internal App Sharing**:
```
PlatformException(sign_in_failed, com.google.android.gms.common.api.ApiException: 10: , null, null)
```
Код `10` у Google Sign-In API — классический `DEVELOPER_ERROR`: SHA-1 сертификата, которым подписан установленный APK, не зарегистрирован как Android OAuth-клиент в Firebase/Google Cloud для этого пакета (`com.riva_psy.app`).

**Настоящая причина, подтверждено фактом (изначальный `google-services.json` имел `"oauth_client": []` — полностью пустой массив, ни одного зарегистрированного Android-клиента вообще):** приложение распространяется/тестируется через **три разных механизма подписи**, и каждый даёт свой уникальный сертификат:
1. **Upload-ключ** (`key_riva_psy.jks`, тот, которым мы сами подписываем `.aab` перед загрузкой) — SHA-1 `03:D6:A1:47:B4:CC:36:9B:93:1E:57:0D:A3:E0:E6:88:28:00:07:FE`.
2. **Play App Signing** (Google переподписывает `.aab` собственным ключом перед раздачей через обычные треки — внутреннее/закрытое тестирование, продакшн) — SHA-1 `5F:62:31:5B:B0:A9:8C:AB:34:4D:51:DD:C1:CF:2F:E1:BD:1E:14:18`.
3. **Internal App Sharing** — задокументированное поведение Google Play: этот механизм (мгновенная ссылка на установку без полного релизного цикла) подписывает APK **ещё одним, третьим, отдельным сгенерированным ключом**, отличным и от upload-ключа, и от Play App Signing.

Пользователь последовательно регистрировала все три SHA-1 как Android OAuth-клиенты в Firebase Console (скачивая обновлённый `google-services.json` и заменяя `android/app/google-services.json` в проекте после каждого шага — файл в репозитории сейчас отражает первые два сертификата; третий (Internal App Sharing) зарегистрирован в Firebase, но локальная копия файла не обновлялась повторно, поскольку сама раздача через Internal App Sharing на функциональность реальных пользователей не влияет — те получают приложение через Play App Signing, чей сертификат уже присутствует). После регистрации всех трёх — вход и регистрация подтверждены рабочими и через Internal App Sharing.

**Побочные, но реальные фиксы, сделанные в процессе диагностики (не диагностика, остались в коде):**
- `_getUsersDocWithRetry()` (`repository.dart`) — retry с задержкой 400мс и обновлением токена при `permission-denied` для чтения `Users`, вместо однократной попытки. Реальная гонка с claims токена, отдельная от истории про сертификаты, тоже существовала и могла давать нестабильные (не 100%-но воспроизводимые) отказы.
- Та же защита добавлена в `createUser()` (запись в `UsersData`) — раньше была полностью не защищена.
- `updateTariff()` (`settings_tariff_activated_screen/repository.dart`) — `await` для `HiveDB.setBox`, было fire-and-forget, могло терять тариф (Орион → Базовый) из-за гонки с последующим `setLocalUserData` без явного `currentTariff`.
- `ServicesAuthService.authWithGoogle()`/`authWithApple()` теперь ловят `catch (e) { print(e); ... }` вместо `catch (_)` — реальное исключение всегда попадает в logcat даже без пользовательского диалога, на случай будущей диагностики.

**Не решено, приостановлено отдельно от этой находки** — см. §58: Flutter-сплэш (`K1Screen`) периодически показывался пустым даже после структурного фикса (`StatefulWidget`/`initState`) и таймингового фикса (`secondsToNewPage` 0→1 сек в `k1_controller.dart`) — последнее подтверждение от пользователя не поступало, пользователь явно попросила отложить разбор сплэша на потом и не считать его блокером публикации.

**Технические требования к реализации**:
- Ипсативный подсчёт: 7 вопросов × 4 варианта, доминанта = максимальный балл, tie-breaker — ответ на вопрос №7. При ничьей — гибридный текст (склейка двух блоков), CTA берётся от доминанты вопроса №7.
- Хранение — локально (Hive, тот же подход, что уже используется для дневника, не вводить Isar как новую зависимость). `test_id`, `dominant_trait`, `answers_array`, `completed_at`.
- Контент — `Map<Enum, Map<String, String>>` (light/shadow/cta_link на каждую доминанту каждого теста), сборка комбинаций на лету, не 72 текста вручную.
- **CTA Action Router** (важно): единый `enum CtaAction` (`energyMatrix`, `desiresScreen`, `challengeThought`, `audioTrack(id)` и т.д.), один центральный роутер сопоставляет enum → реальный маршрут. Тесты и их гибридные комбинации не хранят строки маршрутов напрямую — при переименовании экрана/маршрута правится только роутер.
- Экран "Мой портрет" — генеративная 3D-сфера (частицы/грани, не готовая модель), растёт с каждым тестом, цветовое кодирование по блокам (ядро — тёплое золото/изумруд, паттерны — холодные тона, тень — тёмный обсидиан/сапфир с золотыми прожилками, финал — синхронизация слоёв), карточки-результаты glassmorphism под сферой, hero-анимация карточка→результат, haptic feedback при открытии новой грани. **Технический риск, требует отдельной оценки Code до старта Фазы 1**: генеративная 3D в Flutter нетривиальна (`CustomPainter`+анимация или shader-подход) — если слишком дорого, 2D-альтернатива с той же метафорой (анимированный SVG с частицами).
- Локализация — весь контент (14 экранов результата) на 3 языка. Дисклеймер теста 11 — на всех трёх, не только RU. Связка с записью на консультацию (Cal.com, см. TZ_Konsultatsiya_Cal_com.md) — только RU-локаль, органично после теневых тестов.
