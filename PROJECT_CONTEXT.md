12. **Платежи — ЗАФИКСИРОВАНО РЕШЕНИЕ (2026-07-22): используем только новую схему.**

    В самом ТЗ было два конфликтующих описания оплаты. Решение пользователя: **старая модель считается deprecated и не переносится на PWA.**

    - **~~Старая модель (DEPRECATED, не переносим)~~**: тарифы "Бесплатный"/"Полный доступ", месяц 9€/год 65€, промокоды, автопродление, оплата через Yookassa + In-App Purchase. Уже реализована в текущем Flutter-коде (`yookassa_payments_flutter`, `in_app_purchase`, `settings_buy_subscription_screen`, `settings_payment_subscription_screen`, `settings_tariff_activated_screen`, `tariff_model.dart`), но при переезде на PWA этот код и его бизнес-логику **не переносим и не используем как образец** — сама модель (App Store/Google Play IAP) физически неприменима к PWA.
    - **✅ Актуальная модель (единственная, для PWA)**:
      1. Оплата происходит **на сайте через Stripe Connect**, не в самом приложении/PWA.
      2. **До оплаты** — полностью free-тариф без регистрации: локальный анонимный `device_uuid` генерируется на клиенте без обращения к серверу; весь прогресс/избранное/история хранятся **только на устройстве** (в PWA — IndexedDB/localStorage, аналог Hive); сервер не получает никаких данных о бесплатном пользователе.
      3. **Регистрация происходит только в момент оплаты**: пользователь вводит email на сайте → passwordless / magic link (без пароля) → создаётся `user_id`, привязанный к Stripe Customer ID.
      4. Оплата подтверждается через Stripe webhooks (`checkout.session.completed`, `invoice.paid`, `customer.subscription.updated/deleted`) → backend обновляет статус подписки для `user_id`.
      5. После оплаты сайт показывает кнопку "Открыть в приложении" → **deep link / universal link** с одноразовым токеном → автологин в PWA, выдаётся JWT.
      6. **Миграция локальных данных на сервер**: однократно, локальные данные (привязанные к `device_uuid`) отправляются на сервер и привязываются к `user_id`; конфликты (повреждённые/задвоенные данные) разрешаются в пользу более полной/новой версии, лог конфликта сохраняется для отладки. После миграции `device_uuid` перестаёт быть основным идентификатором.
      7. Дальше приложение при каждом запросе проверяет статус подписки через собственный backend API (JWT-авторизация, не через Apple/Google). Синхронизация между устройствами — только для оплативших/зарегистрированных.
      8. Данные на сервере — минимальный набор: email, статус подписки, прогресс/контент-данные, привязанные к `user_id`, без лишних персональных полей.
    - **Технические зависимости новой модели** (ничего из этого в коде пока нет — строить с нуля под PWA): backend-эндпоинт приёма Stripe webhook; API проверки статуса подписки (JWT); эндпоинт миграции локальных данных (принимает `device_uuid` + payload, возвращает `user_id`); deep link/universal link конфигурация для автологина (на вебе это существенно проще — обычный URL + service worker, без нативных Universal Links/App Links).

### Оценка качества текущей реализации (разобрано 2026-07-22)

Функционально модуль закрывает весь цикл (добавить препарат → назначить время/период приёма → напоминание-попап → список актуальных/по дате → редактирование), и визуально консистентен с остальным приложением (переиспользует `CustomButton`, `CustomTextFormField`, `AppStyle`, `CustomAppBar`). Но по архитектуре и аккуратности кода это заметно наименее доработанная часть кодовой базы:

- **Хранение данных рискованное**: `PillsRepo.updateEvent()` при каждом сохранении **удаляет всю Hive-таблицу и переписывает её заново** поэлементно (`deleteBox` → цикл `setBox`), вместо точечного добавления/обновления одной записи. Если процесс прервётся между удалением и повторной записью — можно потерять все препараты целиком, не только изменяемый.
- **Чтение с побочным эффектом записи**: `PillsController.getPills()` — по сути геттер, но в конце вызывает `repo.updateEvent(pills)`, то есть каждое открытие экрана перезаписывает всё хранилище целиком. Нарушение разделения "чтение/запись", лишняя нагрузка и лишний риск потери данных на пустом месте.
- **Нет обработки ошибок**: чтение из Hive (`jsonDecode` на каждую запись) ничем не защищено — одна повреждённая запись уронет весь экран списка препаратов. Единственный `try/catch` в модуле (`setDurationOfReception`) просто делает `print()` и молча проглатывает ошибку, без обратной связи пользователю.
- **Дублирующая и рассинхронизированная логика**: метод `checkDateInRange` объявлен в двух местах (`PillsController` и `PillsBottomSheetController`) с **разной семантикой** — в одном месте окно ±1 день от даты начала курса, в другом — честная проверка "между start и end". Одинаковое имя, разное поведение — источник будущих багов.
- **Валидация времени приёма кустарная**: часы/минуты разбираются вручную по индексам строки (`text[0]+text[1]`), верхняя граница проверяется как "часы < 24" и "минуты < 60" вместо корректных 23/59 — на границе возможны некорректные значения времени.
- **"Мёртвый" код валидации формы**: в `PillsAddBottomSheet` объявлен `formKey = GlobalKey<FormState>()`, но никогда не оборачивается в `Form` и не вызывается `validate()` — то есть `validator` у текстового поля с названием препарата **фактически никогда не срабатывает**, хотя выглядит так, будто валидация есть.
- **Смешаны два UX-паттерна валидации в одном экране**: для названия препарата — обычный inline-error у текстового поля (`CustomTextFormField.validator`, но нерабочий, см. выше), а для времени приёма — модальное окно с сообщением об ошибке через смену цвета рамки на красный. Две разные идиомы там, где могла бы быть одна.
- **Не убранные следы кодогенерации**: пустые `// TODO: implement onInit`, `// TODO: implement updateTasks` (комментарии остались от исходного DhiWise-шаблона, реализация под ними уже есть, но комментарий не удалён), задвоенный `import` в `pills_list_model.dart` — по мелочи, но показывает, что модуль не получил той же полировки, что и более новые части (например "Обретение").
- **Архитектурно самый "старый" слой**: чистый GetX с ручными вызовами `update()` по всему коду — паттерн более раннего поколения приложения. Более новые фичи ("Обретение": `working_out_irrational`, `happiness_in_focus`, `desires`) уже написаны на `flutter_bloc`/Cubit. Pills остался на старом подходе и не мигрировал вместе с остальными.

**Что стоит сделать иначе при переносе на PWA** (не просто 1:1 переписать, а поправить по ходу):
1. Инкрементальное хранение (добавить/обновить/удалить одну запись в IndexedDB), без полной перезаписи всей коллекции на каждое действие.
2. Убрать побочный эффект записи из операции чтения списка препаратов.
3. Добавить реальную обработку ошибок чтения (устойчивость к повреждённой записи) с понятной обратной связью пользователю вместо silent-fail.
4. Свести валидацию времени к одной корректной реализации (0-23 / 0-59) и к одной UX-идиоме (либо везде inline-ошибки в форме, либо везде модалка — не вперемешку).
5. Либо реально подключить `Form`/`formKey` и `validate()`, либо убрать эту неработающую обвязку, чтобы не создавать ложное ощущение проверки.
6. Убрать дублирующийся `checkDateInRange` с разной семантикой, оставить одну корректную версию.
7. Реализовать состояние на том же стеке, что и остальной PWA (не тащить GetX-паттерн как единственно ради "было так во Flutter") — иначе Pills снова останется архитектурным аутсайдером в новом кодовом стеке.
8. Механизм напоминаний в любом случае переписывается с нуля под веб (Push API + Service Worker вместо `workmanager`) — это уже входит в общий план миграции, но именно в Pills напоминание вызывается напрямую (`WorkManagerService().initService()` из `addPill`), так что стоит сразу закладывать архитектуру напоминаний с учётом и этого модуля, а не только основного дневника.

## 5. Что переносимо / что переписывать заново для PWA

**Переносимо как концепция / 1:1 переиспользуемо в виде спецификации** (не как код, а как источник истины по неймингу и структуре):
- Иерархия сущностей и их названия: эмоции (группы/подгруппы/конкретные эмоции), места, персоны, части тела, записи (СМЭР), тарифы — модели данных (`*_model.dart`, `freezed`-классы) читаемы как спецификация полей даже если Dart-код не используется напрямую.
- Разбиение на экраны и порядок навигации Основного пути — это чистый UX-флоу, воспроизводимый в любом фреймворке.
- Структура графиков (7 типов, что откуда берут данные) — бизнес-логика агрегации переносима как алгоритм (пересчитать на TS/SQL/что угодно).
- Дизайн-токены: `app_style.dart` / `app_decoration.dart` (566+370 строк) — цвета, текстовые стили, отступы, скорее всего экспортируемы в CSS-переменные / Tailwind-конфиг вручную (не автоматически, но как источник).
- Тексты, копирайтинг (все "тёплые" сообщения-подбадривания из ТЗ и Figma) — переносятся как есть.
- Названия роутов/экранов (`k1`...`k70`) — полезны как чек-лист "что вообще нужно построить", по одному экрану на пункт.

**Нужно писать заново (Flutter-специфика, не переносится на веб напрямую)**:
- Вся Flutter Widget-разметка (`*_screen.dart`, `*_widget.dart`) — просто UI-код, придётся верстать заново под веб-стек (React/Vue/etc.).
- GetX/flutter_bloc/provider — состояние управления, замена на веб-стейт-менеджер (Redux/Zustand/Context/etc.).
- Hive/SharedPreferences — заменяются на IndexedDB/localStorage/веб-совместимое хранилище.
- Firebase Auth платформенные SDK (Google/Apple sign-in нативные потоки) — на вебе другой OAuth-флоу (Firebase Web SDK или отдельный auth-провайдер).
- just_audio/flutter_sound/record (запись голоса) — на вебе через MediaRecorder API/Web Audio API, другая реализация.
- awesome_notifications/flutter_local_notifications — на вебе Push API + Service Worker (принципиально другая модель, тем более для PWA это ключевая история).
- workmanager (фоновые задачи) — на вебе через Service Worker/Background Sync, сильно ограниченные возможности по сравнению с мобильной ОС.
- yookassa_payments_flutter/in_app_purchase — не нужны вовсе при новой (веб) модели оплаты из ТЗ; строить Stripe-интеграцию с нуля под веб — что фактически совпадает с тем, что и так предписывает актуальная версия ТЗ.
- pdf/printing (генерация PDF) — на вебе другой инструмент (напр. jsPDF/Puppeteer/серверная генерация).
- circular_slider/sleek_circular_slider (кастомный тач-регулятор) — придётся реализовать заново на канвасе/SVG под веб-ввод (мышь+тач).
- syncfusion_flutter_charts/pie_chart — заменить на веб-чартинг библиотеку (Recharts/D3/Chart.js/etc.), логика графиков (что и как считать) переносится, рендеринг — нет.
- Deep link/Universal Links механизм — на PWA заменяется обычными URL + service worker, сильно проще технически.
- Вся нативная обвязка (Podfile, GoogleService-Info.plist, android/ каталог, xcodeproj) — не нужна для PWA вообще.
